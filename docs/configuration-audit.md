# Configuration support audit — 2026-09-14

The old UI inferred functionality from the first parsed local file and reused Codex-oriented sections for all providers. That was not a provider capability contract. The new editor reads every discovered source separately, displays all nested data, and offers schema-defined settings even when absent from the file. It does not claim to compute effective configuration across user/project/managed/CLI scopes.

## Behavior and guarantees

- Tabs: General, MCP servers, Models & providers, Permissions, Hooks & automation, Features, Plugins & skills, Project config, Environment, System, Raw config. New targets start on General; explicit saved tab choices remain intact.
- Every parsed field remains inspectable, even if unknown to the bundled schema. Fields without validation rules are preserved without findings. Findings appear only when a defined schema rule fails (including an explicit rule forbidding unknown properties). File read/preview diagnostics stay in Raw config.
- `Show available settings` browses the bundled contracts. Nested objects and arrays can be expanded. Known settings can be added to existing files; dynamic maps support adding entries without replacing sibling secrets.
- Schema validation runs on original values before redaction, offline. It uses only bundled trusted schemas, never a `$schema` URL supplied in a user file. Backend saves validate types/enums/constraints and allow repairing a field while retaining unrelated pre-existing findings.
- Unschematized files explicitly say that semantic validation is unavailable and retain the previous existing-scalar-only write restriction. Secrets and provider-owned registries are protected in the backend as well as the UI.
- Environment/header names remain visible but all values are hidden; token-budget settings are no longer mistaken for credentials.
- Saves retain revision checks, atomic replacement and backups. JSONC/YAML saves normalize formatting; JSONC comments and YAML comments are not preserved. TOML array elements are edited through the containing list.
- No personal configuration values were automatically changed by this audit. Browser interaction checks use synthetic fixture data.

## Scope boundaries

This audit covers all configuration adapters previously advertised by the repository, rather than treating installation detection as configuration support. The other catalog entries only check for executables/apps/extensions; no config file adapter existed for them. They now explicitly show **Installation detection only**. Their configuration capabilities are not certified by this change.

Project context discovery is a separate existing feature. This editor does not yet discover arbitrary per-project config files, evaluate managed policy/remote configuration, create missing configuration files, install plugins, authenticate MCP servers, or test server connections. Those operations must not be inferred from the presence of a settings field.

The detection-only entries are: DeepSeek Harness, Pi, OpenHands, Open Interpreter, Warp, Codewhale, DeepSeek Reasonix, GPT Pilot, OH-MY-PI, Deep Agents Code, Crush, Qwen Code, Kilo Code, Grok Build, Dyad, SWE-agent, Prime Agent, Devika, JCode, Bolt, DeepCode, Plandex, MiMo Code, Trae Agent, Codebuff, Kimi Code CLI, Claude Engineer, Open SWE, ForgeCode, Stagewise, OpenCursor, Melty, Kodu, Mistral Vibe, gptme, Command Code, Grok CLI, Devon, Letta Code, AutoCodeRover.

## Maintaining contracts

`schemas/manifest.json` records provenance, review date, field counts and hashes. All schema data is bundled; normal builds and validation need no network. Upstream schemas must be reviewed and re-vendored deliberately. Claude organization-only keys and Cursor internal state fields receive `readOnly` annotations for the user-file editor. Preserve upstream definitions; the OpenCode schema's `models.dev` references are rewritten to a bundled `$defs/ModelsDev` definition. Generate Continue with `zod-to-json-schema` against the pinned package version. Derived contracts are intentionally labeled partial; do not turn documentation examples into restrictive enums or invented defaults.

Run `pnpm test` and `pnpm check` after contract changes. Backend tests compile all schemas offline and exercise malformed values, additions, arrays, secret preservation, stale revisions and TOML formatting. Frontend model tests verify navigation order, category routing, schema discovery and read-only sources.
